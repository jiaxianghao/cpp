# 自测与答案

先口头回答，再展开答案。答不出来的题，回到对应实验实际验证。

1. 镜像和容器有什么区别？同一镜像可以启动两个容器吗？
2. `run`、`start`、`exec` 分别做什么？
3. 容器主进程退出后，`-d` 能让容器继续运行吗？
4. `stop` 之后计数还在，`rm` 之后一定还在吗？
5. `EXPOSE 8080` 能让宿主机直接访问 18080 吗？
6. `127.0.0.1:18080:8080` 的三个部分分别是什么？
7. 为什么客户端访问 `app:8080`，而宿主机访问 `127.0.0.1:18080`？
8. 为什么源码改了、镜像也重建了，旧容器还可能不变？
9. 命名卷与 bind mount 分别由谁管理存储位置？
10. `docker compose down` 与 `docker compose down -v` 有什么差别？
11. C++ 示例为何使用 ENTRYPOINT 和 CMD 两条指令？
12. 如何判断服务进程“存在”和服务“能处理请求”？

<details>
<summary>展开参考答案</summary>

1. 镜像是模板，容器是实例；可以创建多个，每个有自己的可写层。
2. run 新建并启动；start 启动已有容器；exec 在运行容器中增加一个进程。
3. 不能。后台运行并不改变主进程的生命周期。
4. 不一定。可写层随 rm 删除；外部命名卷或 bind mount 中的数据通常保留，需要重新挂载相同位置。
5. 不能。EXPOSE 是元数据，发布端口要用 -p 或 Compose ports。
6. 宿主机绑定地址、宿主机端口、容器端口。
7. 客户端通过 Compose 网络解析 app 并访问容器端口；宿主机使用发布的端口。
8. 旧容器仍关联创建时的镜像，不会自动切换到标签新指向的镜像，需要重新创建。
9. 命名卷由 Docker 管理；bind mount 明确引用 Docker 主机上的文件或目录。
10. down 删除容器和网络，默认保留命名卷；-v 额外删除项目声明的非 external 命名卷及相关匿名卷。
11. ENTRYPOINT 固定可执行程序，CMD 提供可覆盖的默认参数。
12. ps 的 running 说明主进程还在；请求 /health 或观察健康检查可进一步确认应用能响应。健康检查只覆盖它实际检查的内容。

</details>

## 故障题

从下面选两题，先写判断再动手：

- app 没有发布端口，但同一自定义网络中的客户端能访问它，这是否正常？
- C++ 容器打印一句话后变成 Exited (0)，是否说明 Docker 故障？
- Compose 执行 down 再 up 后计数继续累加，数据保存在哪里？
- 只执行 restart 后环境变量没变，应该使用什么操作？

<details>
<summary>展开故障题答案</summary>

- 正常。容器间通过网络和容器端口访问，不依赖宿主机端口发布。
- 正常。该程序的工作就是打印后退出，退出码 0 表示正常完成。
- 在本项目的 `docker-review_counter-data` 命名卷中。
- 修改 Compose 配置后运行 `docker compose up -d` 使配置生效。

</details>
