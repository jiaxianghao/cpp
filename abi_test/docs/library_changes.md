# 被依赖的 C/C++ 库修改后，调用方要做什么？

## 核心判断

修改的是运行时从库中调用的实现，还是已经编译进调用方的信息？只有动态库实现的兼容修改，通常才能通过换库并重启完成更新。

## 头文件、编译、链接、运行

头文件描述函数声明、枚举、结构体、宏、内联函数及模板等。编译器根据这些信息生成调用方机器代码。头文件不是运行时读取的配置文件。

```text
调用方源文件 + 库头文件 → 编译 → 目标文件 .o
目标文件 + 库         → 链接 → 可执行文件
可执行文件           → 启动 → 加载需要的动态库并运行
```

枚举的数值、宏展开、结构体字段偏移以及 sizeof 等信息可能已经进入调用方机器代码。替换库文件不会自动更新它们。内联函数和模板的实现也可能进入调用方，需要重新编译受影响代码。

## 静态库和动态库

- 静态库 `.a`：链接时把需要的目标代码加入最终程序或共享库。替换 `.a` 不影响已有程序；实现变化后至少需要重新链接。头文件变化影响调用方时，还需重新编译。
- 动态库 `.so`：程序通过动态链接调用独立库中的函数。如果 ABI 和业务行为兼容，通常可以只更新 `.so`，然后重启进程。磁盘上的库文件变化不等于运行中进程已经加载新实现。

动态链接也不能解决调用方已编译的常量、布局或分支逻辑过时的问题。

## API 与 ABI

| 概念 | 含义 | 检查的问题 |
| --- | --- | --- |
| API | 源代码接口 | 旧源码是否能使用新头文件重新编译 |
| ABI | 二进制接口 | 旧二进制是否能直接与新库协作 |

ABI 涉及符号名、调用约定、参数和返回值传递、类型大小与对齐、结构体布局、C++ 虚表等。源代码兼容不代表二进制兼容。ABI 兼容也不代表业务行为一定符合预期。

## 常见修改的处理

| 修改 | 动态链接调用方 | 静态链接调用方 |
| --- | --- | --- |
| 仅修改函数内部算法，接口保持兼容 | 通常换库并重启即可 | 更新库后重新链接 |
| 保留旧接口，新增独立函数 | 旧程序一般可继续使用；使用新函数的代码需重编链接 | 使用新函数的程序需重编链接 |
| 修改枚举既有数值、宏、编译期常量 | 重新编译受影响的调用方 | 重新编译并链接受影响的调用方 |
| 末尾追加枚举值 | 检查底层类型、计数值、范围判断及新值处理 | 同样检查；需要新库实现还要重新链接 |
| 修改跨库结构体布局 | 通常需同步重编相关模块，或保留旧接口另增新接口 | 同样需同步更新 |
| 修改函数参数、返回类型 | 不应假定兼容；检查并同步更新调用方 | 检查并同步重编链接 |
| 修改头文件中的内联函数、模板 | 重编受影响调用方，不能只换库 | 重编受影响调用方 |

### 枚举的典型问题

```cpp
// v1
 enum Cmd { START = 0, STOP = 1, CMD_NUM = 2 };
// v2
 enum Cmd { START = 0, STOP = 1, PAUSE = 2, CMD_NUM = 3 };
```

旧程序中的 `cmd < CMD_NUM` 已经相当于 `cmd < 2`，换库不会让它变成 `cmd < 3`。旧 switch 也不会凭空出现处理 PAUSE 的分支。

末尾追加通常能保持原有值，但要注意：插入到中间可能改变后续隐式数值；新增值过大或启用 `-fshort-enums` 可能影响类型大小；枚举计数若决定跨库结构体中的数组长度，也可能改变布局。显式指定底层类型有助于固定大小，但不能解决旧逻辑不认识新值的问题。

### 结构体的典型问题

把 `struct Vehicle { int speed; int gear; };` 改为 `struct Vehicle { int speed; int mode; int gear; };` 后，旧程序认为第二个 int 是 gear，新库却认为它是 mode。双方可能访问错误字段甚至越界。

末尾追加字段也未必安全：调用方分配大小、数组步长以及按值传参方式都可能受影响。库内部私有结构、由库自己分配管理的不透明对象，则需要根据实际边界判断，不能与公开结构体一概而论。

## 实际排查顺序

1. 明确修改前后版本，以及哪些进程需要新功能。
2. 确认实际链接方式，查看 CMake、链接命令和二进制依赖。
3. 检查公开头文件：常量、枚举、结构体、函数签名、内联函数、模板。
4. 检查新值是否流入旧程序，旧程序是否有范围检查或缺失分支。
5. 只更新受影响的构建和部署产物，并验证完整调用链。

Linux 下可用 `readelf -d 程序` 查看直接动态依赖。没有某个 NEEDED 项不总能证明它被静态链接，也可能通过其他共享库间接依赖或 dlopen 加载，应结合链接命令判断。

## 当前 uos 项目中的例子

本次查看的源码中：

- `uos_core/CMakeLists.txt` 将目标 `uos_core` 明确定义为 STATIC，另有 `uos_core-shared` 目标。
- `uos_operation/CMakeLists.txt` 的主程序链接列表使用 `uos_core`，因此 core 的相关实现进入主程序。
