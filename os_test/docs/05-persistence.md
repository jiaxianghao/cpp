# 持久化：写成功之后数据在哪里

## 从设备到文件

驱动通过设备接口发起 I/O。轮询主动检查完成状态，中断让设备通知 CPU，DMA 使设备能够在内存与设备间传输数据，减少 CPU 逐字节搬运。机械磁盘有寻道和旋转成本；SSD 仍有擦除、写放大、回收等约束。

目录把文件名映射到 inode 等文件标识；inode 保存元数据和定位数据块的信息。文件描述符引用进程的打开文件资源，打开后不必每次再按路径查找。

同一文件可以有多个硬链接。移除某个名字不必立即销毁文件；只要仍有其他链接或打开引用，其内容仍可能可访问。符号链接则保存路径，目标路径失效时可能成为悬空链接。

## write、rename 和 fsync 分别承诺什么

普通缓冲 I/O 的 `write` 成功通常表示内核接受了数据，不代表掉电后一定保留。C/Python 的用户态缓冲还要先 `flush`；`fsync` 用来请求同步文件数据及相关元数据。

同一文件系统内用 rename 替换名字，能提供路径查找意义上的原子替换。已经打开旧文件的读者仍可继续读旧内容；新打开的读者看到新文件。这与“原地覆盖时读者可能看见半份数据”不同。原子替换不等于持久化保证。

Linux 本地文件系统中常用的发布顺序是：

```text
在目标目录创建临时文件
→ 完整写入新内容
→ flush 用户态缓冲
→ fsync 临时文件
→ rename/replace 到目标名字
→ fsync 父目录
```

最后一步用于同步目录项变更。此流程依赖文件系统、挂载方式和设备正确实现同步语义；跨文件系统移动不是同样的原子操作。实验 7 演示调用顺序和文件引用行为，没有模拟掉电，成功运行不构成断电恢复验证。

## 文件系统为什么需要日志

创建或扩展文件可能同时修改数据块、inode、目录和空闲空间位图。若只完成一部分就掉电，结构可能不一致。文件系统日志先记录事务所需信息，再提交，恢复时据此恢复一致状态；不同日志模式对用户数据的保护不同。日志不自动保证应用层多个文件的任意更新具有事务语义。

FSCK 根据结构检查并修复不一致，可能需要大量扫描。LFS 把更新组织成追加式写入，之后要清理旧段。校验和帮助发现损坏，修复还需要可用的冗余副本。RAID 提供某些设备故障下的冗余，但误删、错误覆盖仍可被同步传播，所以不是备份。

复习抓手：对每个操作分别问“其他进程什么时候能看到”“崩溃后什么时候能保留”。两个答案经常不同。
