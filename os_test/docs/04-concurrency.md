# 并发：保护共享数据的不变量

## 从一次加一开始

`counter++` 通常涉及读、加一、写回。两个线程可能都读到 10，都写回 11，从而丢失一次更新。对普通 C 对象无同步地并发读写会构成数据竞争，产生未定义行为；不要把某次输出当作可靠实验结论。`volatile` 不提供线程同步。

实验 5 使用 C11 原子对象，将“读”和“写”拆开，并用屏障强制两线程都先读完再写，因此能稳定展示逻辑层面的丢更新，同时避免普通变量的数据竞争。单次原子读写并不意味着整个读改写事务原子。用互斥锁包住整个更新，或使用 `atomic_fetch_add`，才能修正这个计数例子。

本包保持默认顺序一致的原子内存序，先理解操作边界，不在第一轮引入弱内存序。

## 锁保护什么

锁应保护不变量，例如“队列中的元素个数与读写位置一致”。所有访问相关共享状态的线程应遵守同一锁协议。只在写入时加锁，读取时随意访问，仍可能有问题。

互斥锁只允许一个线程进入临界区。自旋锁忙等，阻塞式锁在竞争时可以使线程休眠；实现可能结合两者。不能简单认为自旋总比休眠快，需考虑持锁时长、CPU 数量和调度。

## 条件变量：等条件，不是攒通知

消费者要等“队列非空”，生产者要等“队列非满”。典型写法：

```c
pthread_mutex_lock(&mutex);
while (!predicate) {
    pthread_cond_wait(&changed, &mutex);
}
/* 使用或修改受 mutex 保护的共享状态 */
pthread_mutex_unlock(&mutex);
```

`wait` 原子地释放锁并开始等待，返回前重新获得锁。返回后必须重新检查条件：可能有虚假唤醒，也可能条件已经被另一个线程消费。条件变量不存储通知次数；真正需要保存的是共享状态。实验将状态修改与通知放在同一把锁的保护下，便于推理。

信号量维护计数，`wait` 获取一个额度，`post` 增加额度；通知发生在等待之前也能体现在计数里。单槽队列可用 `empty=1`、`full=0` 和互斥保护实现。

## 死锁与事件循环

线程一持有 A 等 B，线程二持有 B 等 A，会形成循环等待。死锁的四个必要条件是互斥、占有并等待、不可抢占、循环等待。统一获取锁的顺序是常见解决方法。超时可以避免无限等待，但还要正确回滚，不能仅凭加了超时就宣称问题已解决。

事件循环通过就绪事件驱动任务，能减少共享状态与线程切换，但长时间计算或阻塞调用会拖住整个循环。多线程与事件驱动都需要明确状态和资源生命周期。
