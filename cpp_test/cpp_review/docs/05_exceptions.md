# 异常安全与事务式更新

## 核心回顾

异常安全不是“每个函数都 try/catch”。首先保证资源由对象拥有，再定义操作失败后允许留下什么状态。

|保证|失败后的要求|示例|
|---|---|---|
|基本保证|没有资源泄漏，类不变量仍成立；状态可改变|向合法列表加项后校验失败|
|强保证|操作失败对约定的状态无可观察修改|先更新副本，成功后 swap|
|不抛出保证|操作不让异常逃逸|适当的析构和提交步骤|

构造函数抛出时，完整对象没有构造成功，不调用该对象自身的析构函数；已完成构造的基类和成员会清理。普通裸指针成员不会替你释放其指向的资源，这正是 RAII 成员的重要性。

强保证常用“准备—提交”：所有可能失败的工作先在临时状态上完成，最后用不抛出的操作提交。它有复制成本，不能不加分析地扩展为外部支付、日志、网络等副作用全部可回滚。必须说明保证覆盖的状态范围。

按 const 引用捕获异常避免复制和切片；重新抛出原异常用 `throw;`，`throw e;` 可能复制并丢失动态类型。析构一般不应抛出；异常传播导致栈展开时，析构再抛异常会 terminate。noexcept 是边界承诺，异常逃出该函数时 terminate，而不是编译器禁止函数里出现 throw。

## 实验与解读
