# 重构：让行为保持不变的小步修改

## 建立判断标准

重构是在保持可观察行为的前提下改善内部结构。添加新折扣规则是功能变更；把旧折扣规则提炼到函数是重构。修复一个原有错误会改变行为，应该明确记录为修复，别混在“纯重构”里。

代码异味是调查线索，不是必须立即套模式的命令。长函数可能承担了多个步骤，重复代码可能缺少一个概念，过长参数列表可能隐藏一个领域对象；但两个看似相同的分支也可能因为不同业务原因而独立变化。先确认变化原因，再决定是否合并。

## 实验中的真实约束

阅读 [源码](../examples/08_refactoring.cpp)。金额以分计，会员先乘 9 再除 10，使用整数截断。**折后金额**小于 10000 时加 800 运费，否则免运费。原行为甚至包含空订单收费 800；这不是对合理业务的推荐，而是为了练习保留现有行为。

重构前，before 把计算小计、折扣、运费混在一起。重构后，after 使用 discounted_subtotal 和 shipping_fee 表达三个步骤。没有引入继承，因为当前只需让规则更清晰。

先预测：原价 10000 的会员订单最终收多少？11111 与 11112 在会员折扣后有什么差别？如果把是否包邮的判断移到折扣前，是否还是重构？

## 可操作的工作流程

1. 写特征测试，记录旧代码目前的可观察行为，不先假定它完全正确。
2. 用具体业务期望补充测试：普通订单、会员、整数截断、恰好达到边界、边界两侧、空输入。
3. 只提炼小计计算，构建并测试。
4. 提炼运费计算，构建并测试。
5. 改善变量与函数命名，保持求值顺序和异常行为。
6. 查看 diff，确认没有夹带规则修改，再处理下一项需求。

```bash
cmake --build build --target 08_refactoring
./build/08_refactoring
ctest --test-dir build -R 08_refactoring --output-on-failure
```

源码提供独立的期望值和较宽输入范围的前后差分检查。仅比较 before==after 可能让两边共同的错误通过，所以不能代替业务期望值。

## 常见手法与使用条件

|手法|触发线索|避免的误用|
|---|---|---|
|提炼函数|某一段有稳定的业务含义|把每一行都拆成跳转|
|引入参数对象|若干参数总是表达同一概念|为不相关参数造万能结构|
|拆分阶段|解析、计算、输出互相纠缠|提前建设通用流水线框架|
|移动函数|行为主要依赖另一个对象的数据|只按文件长度机械搬家|
|以多态替代条件|多个稳定变体反复影响同一组操作|一个简单 if 就建立类树|
|内联函数/类|间接层不再带来清晰度|认为抽象只能增加不能删除|

## 动手练习

先保留 before 不动，在本地从 before 复制一个 practice 函数，每次只完成一个提炼步骤，并把 practice 加入现有测试。接着单独增加“空订单收费 0”的新需求：先改期望使测试失败，再修改行为。说明为什么这第二步属于功能修改。

过关标准：能指出原代码全部业务边界，解释一次失败测试捕获了什么行为变化，知道何时撤回没有收益的抽象。
