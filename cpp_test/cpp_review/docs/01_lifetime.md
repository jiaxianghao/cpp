# 生命周期、初始化与 const

## 核心回顾

对象有存储不等于已经完成初始化。局部自动对象离开作用域时销毁；成员按**声明顺序**初始化，按逆序销毁。初始化列表的排列不会改变这个顺序。基类先于成员构造，析构顺序反过来。

`const int*` 限制通过该指针修改整数，`int* const` 限制改变指针指向。const 视图不意味着底层对象永远不变；别的合法可写别名仍可以修改它。`const` 成员函数通常表达不修改对象的可观察状态，`mutable` 应有明确语义，例如缓存，而不是随意绕过约束。

返回局部对象的引用会悬空；返回对象的值通常才是正确接口。把临时量绑定到局部 const 引用可以在特定规则下延长生命周期，但不能把“引用会延寿”泛化到返回引用、引用参数或所有成员情形。

优先在初始化列表中直接构造成员。const 成员和引用成员必须在那里完成初始化；先默认构造再赋值可能做了多余工作。

## 先预测

1. `Pair` 析构时，first 和 second 谁先销毁？
2. `read_only` 最终读到 7 还是 9？为什么没有违反 const？
3. 如果把 second 写到初始化列表前面，能改变初始化顺序吗？

## 实验与解读

运行 `./build/01_lifetime`。前四行应为 `+first`、`+second`、`-second`、`-first`，最后为 `const view sees 9`。将声明顺序对调，同时调整初始化列表，重新解释输出。不要只记“后进先出”，要指出这里的进入顺序来自哪里。

日志类只是可视化工具：析构期间调用可能分配内存的日志接口在生产系统中需单独考虑失败行为。
